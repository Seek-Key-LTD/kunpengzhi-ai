## 一、Vision：Leap Forward Web 4

任务分配从「武断 assign」进化为「**市场竞标（Auction）**」——这是迈向 **Web 4** 的基础：

```
Web 1.0  只读（人看内容）
Web 2.0  读写（人生产内容）
Web 3.0  确权（链上所有权 / EVM 微支付 — key-agent 12 席钱包已就绪）
Web 4.0  自治（agent 市场：任务即商品，agent 竞标服务 — 本设计）
```

**核心理念**：不武断分配任务（"塞给谁"），而是**发布 → 竞标 → 服务**——由市场（拍卖）决定谁服务，agent 凭能力与报价获得机会。

## 二、需求：Auction 分配机制

### 1. Task 类型区分（先分类，再设计标书）

| 类型 | 特征 | 例子 |
|------|------|------|
| **编译类（Compilation）** | 可验证产出、有明确规格、依赖确定性 | 代码编译、配置渲染、文档生成、底包分发 |
| **调查类（Investigation）** | 开放探索、证据收集、结论不确定 | 法理调查、地缘分析、素材研究、市场调研 |
| （预留）创作类 / 推理类 | 需进一步定义 | 辩论陈词、剧本创作、策略推演 |

### 2. Task 属性（proposal/标书的输入）

每个 task 需要声明（决定竞标复杂度与依赖）：

- **依赖数**（dependency count）：该 task 依赖多少外部资源/上游产出
- **复杂度**（低/中/高）
- **紧急度**（deadline / SLA）
- **预估工时**（参考 keyagent 现有 `estimated_hours`）
- **验收标准**（编译类=可构建通过；调查类=证据链/报告结构）
- **所需能力**（模型、工具、记忆库访问）

### 3. Proposal（标书）本身需要严谨设计

标书（agent 的投标）至少包含：

```
agent_id（谁投）
task_id（投哪个）
报价（credit / 微支付单位）
工期承诺
能力自评（匹配度）
依赖清单（需要的上游/工具/记忆）
验收理解（怎么算完成）
```

### 4. 竞标流程（1 分钟拍卖）

```
ticket（issue）发布 → 进入拍卖窗口（60s）
  → 广播给 24 席（webhook → keyagent，复用已验证的接活链路）
  → agent 提交标书（proposal）
  → 时间到 → 按规则选赢家（最高报价 / 最优匹配 / 综合评分）
  → 通知赢家 → 赢家获得服务该 ticket 的机会（日历占用 + 任务建单）
```

### 5. 竞价单位（候选）

- **Credit**（积分，keyagent 现有机制）
- **EVM 微支付**（12 席钱包 + Base Sepolia，distribute_12_seats.py 已初始化）
- 组合（credit 资格 + 微支付结算）
